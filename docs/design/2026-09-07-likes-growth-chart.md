# 累计喜欢曲线的时间维度

## 变更记录

| 时间 | 说明 |
|------|------|
| 2026-09-07 | 新增事件表，曲线按累计人数绘制，时间窗滚动切换 |
| 2026-09-07 | 时间窗改为 1 周 / 1 月 / 半年 / 1 年 / 全部；去掉 1 天 |
| 2026-09-07 | 默认时间窗改为最近 30 天 |

## 背景信息

页面只有一个总人数，画不出随时间增长的曲线。若按「一天一张表、一周一张表」分别聚合，同一天在不同按钮下会对不上，也和 GitHub star 图不一致。star 图的纵轴是到该时刻为止的总数，横轴是日历时间；日/周/月是看多长一段，不是三种统计口径。

## 当前方案

`likes.clicks` 仍是展示用总人数（含历史上没有时间戳的基数）。每次 `bumpCount` 再往 `like_events` 插入一条 `created_at`（Unix 毫秒）。

曲线点：窗口起点的累计值 + 窗口内每个事件 + 当前时刻。累计值 = 总数 − 事件条数 + 该时刻及以前的事件数。基数没有历史日期，只作为起点水平线；之后从主题点进来的喜欢才会让线上升。

时间窗是滚动窗口，不是自然周/自然月，也不是按天预聚合后再查：

| 按钮 | 窗口 | 横轴刻度 | 纵轴 |
|------|------|----------|------|
| 1 周 | 最近 7×24 小时 | 月/日 | 贴可见区间放大 |
| 1 月 | 最近 30×24 小时 | 月/日 | 贴可见区间放大 |
| 半年 | 最近 180×24 小时 | 月/日 | 贴可见区间放大 |
| 1 年 | 最近 365×24 小时 | 跨年用年/月 | 贴可见区间放大 |
| 全部 | 首条事件至今；不足 30 天则补到 30 天 | 跨年用年/月，否则月/日 | 从 0 起，贴近 GitHub 全历史图 |

每次喜欢写一条时间戳。切窗口时只是用不同的起止时间去切同一批事件，没有「每天一张快照」表。

## 其他模块引用约束

计数只能走 `bumpCount`（`GET /?from=theme` 或带约定头的 `POST /api/click`），以便事件与总数一起增加。不要只改 `likes.clicks`。曲线数据嵌在首页 HTML 的 `#like-history` 里，不是按窗口再请求。

## 工程师测试验收方法

打开首页末尾：默认「1 月」，横轴约最近 30 天、纵轴贴可见人数。切换 1 周横轴仍为月日，1 年出现年/月，「全部」纵轴从 0 起。用 `/?from=theme` 计一次后刷新，对应窗口应出现上台阶。`GET /api/count` 仍返回总数。
